阿里云 Qoder / QoderWake / 千问办公：多人多 Agent 协同与项目能力洞察（信息收集 + 分析稿）

用途：为华为云码道 CodeArts 竞争洞察一页 PPT 做前置的信息收集与分析。 信息截止：2026-09-26（云栖大会 2026 于 9 月 22–24 日在杭州举办，主题"智以致用"）。 说明：本文所有事实性描述均标注来源编号，见文末"参考资料"。带【推断】标记的内容为基于公开信息的分析判断，非官方表述。

0. 一句话结论

阿里在云栖 2026 上，把"多人多 Agent 协同"同时落到了三个入口：Qoder（研发协同：项目 + 讨论 + Agent Team）、QoderWake（组织协同：常驻 IM 的数字员工团队 + 多层记忆 + 自进化）、千问办公（业务协同：企业上下文 + 协作空间 + 数字员工身份）。三者共用 Qoder Agent Harness / 千问模型 / 阿里云 Agentic Cloud 底座，其共同战略意图是：把 Agent 从"个人桌面工具"升级为"组织成员"，让 Agent 成为云上 7×24 常驻的"居民"，持续消耗算力、存储、网络与 Token，并借此完成"从运营算力到运营智力"的商业模式切换。

1. 背景：云栖大会 2026 的顶层叙事（理解三款产品的钥匙）

层级 发言人 核心观点 与本洞察的关系
集团战略 吴泳铭（阿里 CEO） 进入"机器智能时代"，机器思考总量将达人类 1000 倍；三大基石 = AI 模型、AI 芯片、AI 云；"Agent 需要长时间执行任务……都会成为云上的'居民'，持续调用算力"；目标 2032 年阿里云全球数据中心超 20GW [R1][R2] Agent 常驻 = 云资源持续消耗，是 QoderWake 云端化、Cloud Agents 的根本商业动机

算力 高慧（平头哥） Agent 执行时短时间高频调用模型，对计算、网络、存储协同要求极高，走向"算网存协同" [R4] 多 Agent 并发 = 通算（CPU/存储/网络）与智算同步增长

【推断】阿里的产品叙事已经从"AI Coding 工具"转到"组织级 Agent 基础设施"。吴泳铭甚至把"今天的 AI Coding"类比为"电气时代早期的电灯"[R2]，暗示编程 Agent 只是入口，真正的增量在其后的 Agent 常驻工作负载。

2. Qoder：从 AI IDE 到"以编程智能体为核心引擎的智能体平台"

2.1 产品概况

  • 2025 年 8 月 Qoder IDE 首发；2026 年 8 月底"全新 Qoder"发布，定位"面向所有人、以编程智能体为核心引擎的智能体平台"；全球用户超 600 万、服务超 10 万家企业 [Q1][Q2]。
  • 七大产品形态：Qoder 桌面端、Qoder IDE、Qoder CLI、JetBrains 插件、移动端（远程控制）、QoderWake 数字员工、Qoder Cloud Agents 云端智能体，各终端任务状态互通 [Q2]。
  • 底座：Agent Harness（规划-执行-验证-纠错循环、分级权限、工具白名单）；Auto 多模型调度（Qwen3.8-Max 等）；40+ 连接器、70+ 插件、2 万+ 技能；Plan / Goal / 侧边任务三大长任务机制 [Q1][Q2]。
  • 工作范式主张："工作的对象从代码工程变为智能体任务，工作的姿势从亲手生产变为委派与验收" [Q1]。

2.2 "项目（Projects）"功能（2026-09-23 云栖发布，企业版内测）

来源：Qoder CN 更新日志 [Q1]、官方文档"项目" [Q3]、媒体报道 [Q5]

维度 能力细节
定位 组织需要多人协作的研发工作（新功能、缺陷修复、技术改造），"与 Agent 在同一空间讨论方案、推进任务"
结构 项目 → Issue（待办）→ 看板；Issue 含标题、目标/背景/完成条件、优先级、状态

2.3 "讨论（Discussion）"功能（同日发布）

来源：官方文档"讨论" [Q4]、媒体 [Q5]

维度 能力细节
定位 与同事和专业 Agent 讨论需求、评审方案、分析缺陷，并记录结论和后续安排
交互 添加设计文档/截图等上下文附件；引用回复；@ 成员或 Agent；"关键消息"标记（结论集中查看、定位原消息）；消息搜索、固定到侧栏
Agent 参与 通过"分享 > 添加 Agent / Agent Team"把自定义 Agent 或 Agent Team 加入讨论；@Agent 请其分析材料、比较方案、补充测试思路；可"查看执行对话"审查 Agent 执行记录
关键限制 只有 Agent 的拥有者可以 @ 它；不能调用其他成员的 Agent；Agent 执行在拥有者当前设备上，需设备在线 [Q4][Q6]
典型场景（官方示例） "支付幂等方案评审"：后端介绍现有实现、测试补充异常场景、Agent 比较候选方案、"本次只分析，不修改代码"

2.4 自定义智能体 & 智能体团队（Agent Team）

  • 自定义智能体：为代码审查、方案规划等固定工作保存指令、模型、权限、Skills/MCP/Plugins、工具白/黑名单；开启"允许在 Issue 和讨论中使用"后可被 @ [Q6]。
  • 自定义智能体团队：指定 1 名负责人 + 1–4 名成员；"协作指令"定义分工与要求；负责人拆解、协调、汇总，交由人审阅；团队任务通过当前设备执行 [Q7]。
  • CLI Agent Teams：main Agent 动态创建 teammate（researcher / coder / reviewer），SendMessage 协调，shared Task list 记录 owner/状态/依赖；建议 2–4 成员 [Q8]。
  • Cloud Agents Multiagent 编排：Coordinator 委派子 Agent（各自独立 Session Thread）+ Advisor（只给建议不执行工具）[Q9]。

【观察】Qoder 的多 Agent 编排有三套并行实现（桌面 Agent Team / CLI Agent Teams / Cloud Multiagent），说明产品仍在快速迭代期，尚未统一。

2.5 云端能力与商业化

  • 云端自动化（9/23）："有可用云环境的账号，可通过对话或配置创建定时任务，在桌面端查看执行记录、继续追问" [Q1]。
  • Qoder Cloud Agents 1.0（9/17）："Agent as a Service"，一站式云端 Harness 托管；Forward Mode（企业/模板/用户三级配置、内建钉钉/飞书/微信/企微 IM 渠道、Schedules、终端用户 Identity）与 Managed Mode（原子 API：Agent / Environment / Session / Event，组织级 Environment、Skill、Vault、File、Memory Store）[Q10][Q11]；Environment 支持 cloud（托管容器，Ubuntu 22.04，/data 工作区）和 self_hosted（外部 worker 通过 Work API 拉取任务）[Q12][Q13]。
  • 计费：Credits 制。模型调用按 Token 折算；云沙箱按 Session running 状态按秒计费、按小时结算，沙箱通常占单次 Session 总消耗 5%–10%（2026-08-10 起正式收费）；企业空间使用"服务账号专用资源包"（阿里云云市场购买）[Q14][Q15]。
  • 企业版内置云端知识库 QMind（跨设备、团队共享），ISO/IEC 27001:2022 认证 [Q2]。

2.6 Skill 自进化建议（9/23）

会话完成后，从可复用经验中获得 Skill 创建/更新建议；采纳后进入独立会话，确认方案后再执行 [Q1]。—— 这是 QoderWake 自进化机制向 Qoder 桌面端的"下放"。

2.7 现阶段短板（对比时可用）

  1. 项目/讨论仍是"轻量 Issue 看板 + 群聊"，没有需求管理、迭代、里程碑、工时、代码评审、流水线等 DevOps 深度能力；结论回写 Issue 靠人工。
  2. 成员邀请仅限链接，未接入企业组织架构；Agent 不可跨成员共享调用。
  3. Agent 执行依赖拥有者设备在线（桌面端），与云端执行尚未在协作场景打通。
  4. 功能处于内测，仅企业版。

3.2 数字员工的构成与"员工-工位分离"设计

  • 五层构成：身份、记忆、技能、分工、权限红线 [W1]。
  • "雇主-员工关系"：起名字、定岗位、画红线；"换设备、换 LLM 引擎、换工位，他还是同一位员工"；人格档案是可 git 管理的纯文本；"订阅期过了，训练成果不会消失" [W1]。
  • 员工与工位分离："员工保存身份、记忆、技能和权限；工位负责提供运行环境，可以是本地电脑，也可以是云端沙箱"；邀测期默认住在用户设备上，"代码上不上云、记忆放不放云端，由你决定" [W1]。
  • 权限：每个 Waker 内置权限中心，从工具调用、文件访问、内置能力、模型输出四个维度独立开关；管理员可配组织级权限；高危操作默认拦截、命中规则需人工授权 [W4]。

3.3 多人多 Agent 协同能力

能力 细节 来源
Waker 群组（Group） 多个本机或远程 Waker 加入同一群组，指定 Leader 接收任务、拆解、分派、汇总；每位成员独立配置模型和工作目录；"谁跑在哪台机器上不影响一起干活"；群技能 + 协作 SOP 明确分工（谁思考拆解、谁执行、谁验收、哪些场景转人工）；可切换协作模式（头脑风暴放宽 vs 生产交付严格） [W2][W3][W4]
人机混合团队 "N 名员工 × M 个数字员工"；同一业务群可加入多名不同职能 Waker，系统按消息内容、岗位职责自动分发 [W4]
WakerFlow 自然语言生成多步骤、多 Waker 流程；手动/定时/事件/API 触发；节点级输入/思考/工具调用/输出可视；版本历史与回滚；可分享给其他团队复用 [W2][W4]
专家求助机制 Waker 在缺信息或需专业判断时，按"专家标签"私聊真人专家，专家引用回复后结论回到原任务与群聊，并沉淀进记忆/知识库 [W6][W7]

3.4 结合 IM 的能力（这是 QoderWake 与 Qoder 的最大差异）

  • 已打通钉钉、飞书、企业微信三大办公 IM，另支持个人微信、QQ 机器人多实例管理；原生读取组织架构、在线文档、多维表格、待办、日历；可操作钉钉文档、读取钉钉会议听记 [W2][W3][W4]。
  • @Waker 统一入口：群里只需一个机器人，后台按职责路由到多位 Waker；配对模式（按会话审批）与开放模式 [W2][W6]。
  • 觉醒模式（Wake-up Mode）：开启后 @Waker 识别成员意图、路由任务、记录后续补充与执行结果，并在聊天内沉淀"话题"和"记忆" [W6]。
  • 常驻群聊上下文：持续接收群内全部消息，自动区分"任务补充 / 需求修改 / 全新任务"，自主决定承接、转交其他 Waker 或求助真人专家；一个群窗口多任务并行；多人同时发消息自动排队；执行中可插话中断并基于当前上下文继续 [W4]。
  • 白天在群里与人确认口径，夜间沿用白天确认的规则无人值守执行，第二天回群继续迭代——"同一个数字员工贯穿全天候" [W4]。
  • 群聊答疑专员"Q仔"：上线 5 个月服务 10 万内部员工、8.6 万次对话、日均 1500+ 条消息；知识库能答的直接答，不能答的找专家，确认后回群并更新知识库 [W4]。

3.5 项目能力

  • 公开项目 / 私有项目：公开项目是"多个 Waker 可复用的工作目录"，一个账号下所有 Waker 共享项目里的上下文与产物；私有项目仅当前 Waker 使用 [W2][W8]。
  • 项目来源支持本地目录或 Git 仓库地址；IM 渠道可绑定工作目录/项目；项目记忆（目录结构、项目约定、测试命令、稳定业务背景）作用于"选择了该项目或目录的任务" [W2][W9]。
  • 【观察】QoderWake 的"项目"是"工作目录 + 项目记忆"的概念，偏 Agent 执行上下文；Qoder 的"项目"是"Issue 看板 + 讨论"的概念，偏人类协作管理。两者尚未打通。

3.6 记忆体系：已具备多层级雏形，但缺"企业记忆"一层

官方五种记忆范围（docs "记忆系统"）[W9]：

范围 适合保存 生效范围
个人记忆（Waker 级） Waker 的长期职责、输出偏好、通用规则 该 Waker 后续任务
项目记忆 目录结构、项目约定、测试命令、稳定业务背景 选择了该项目的任务
群共享记忆 群内所有成员都应复用的事实、约定、结论 当前 @Waker 群聊
成员记忆 某位群成员的职责、偏好、协作习惯 当前群聊中的该成员
单聊记忆 机器人与某成员单聊的长期上下文 当前 @Waker 单聊

官方"四层上下文"叙事（1.0 发布稿）[W4]：岗位档案（职责/边界/红线）→ 现场协同上下文（IM 群讨论、附件、共识）→ 已确认记忆（每日自动复盘，只留经人确认的口径，区分公开共识与私人对话）→ 可复用技能（验证过的指标口径、答案、流程）。

记忆治理能力：整份 MEMORY.md 可编辑、版本管理与回滚、记忆时间线（按日期/来源筛选）、跨机器导出导入迁移、空闲轮次后台自动沉淀核心记忆、"同一规则只在最小必要范围保存"原则、Anti-Rot 淘汰过时记忆 [W2][W9]。

对"多层记忆演进"问题的判断【推断】：

  1. QoderWake 已经实现"个人（Waker）/ 项目 / 群 / 成员 / 单聊"五层，这本质上已经是个人记忆、项目记忆、群记忆三层 + 两个人际子层。
  2. 企业记忆这一层目前不在 QoderWake，而在千问办公的"企业上下文（Enterprise Context）"——它支持"公司层面 / 部门知识空间"分级、周期性刷新、专属压缩模型 [T2][T3]。同时 Qoder Cloud Agents Managed Mode 已有组织级 Memory Store 资源 [Q11]。
  3. 因此阿里的多层记忆版图是"分布式的"：个人/项目/群 → QoderWake；企业 → 千问办公企业上下文 + Cloud Agents Memory Store。下一步极有可能是让 QoderWake 的 Waker 直接挂载企业上下文，形成个人-群-项目-企业四级贯通（束骏亮称企业上下文"像数据库一样，不属于任何一个 Agent 产品，而属于企业客户本身" [T6]，为这种挂载留了口子）。
  4. 对码道的含义：研发场景天然有清晰的"个人 → 项目/代码库 → 团队/部门 → 企业（规范、架构资产、安全基线）"层级，比办公场景更容易做成结构化的多层记忆；这是码道可以先于对手做深的地方。

3.7 长期记忆 + 持续进化（成长轨迹、自进化）

来源：QoderWake 发布博客 [W1]、更新日志 [W2]、第三方解读 [W10]

  • Harness-First 架构：确定性编排器（Orchestrator）负责长时程流程，模型负责意图理解与推理，Brain-Hands-Session 解耦；Executor 即时验证 + 独立 Verifier 审查整体结果，失败触发 REWORK 且失败原因沉淀为知识；Session 作为唯一状态源，任一组件崩溃可幂等重建。
  • 执行即经验："第 1 天是初始基线，第 90 天是深度适配个人和企业的专家级经验，时间积累成为产品能力的一部分"；知识引擎跨多次执行提炼隐含规律（例："支付模块变更必须保持事务结构"）。
  • Experience-to-Capability 三层：① 对话、工具调用、记忆召回、验证结果、用户纠正、重做等多维事件统一为结构化可学习信号；② 基于完整任务轨迹做归因，判断经验应沉淀为记忆 / 技能 / 策略 / 验证器 / 工作流五类；③ Anti-Rot Governance 防腐治理：监控、验证、降权、合并、撤回——过时记忆淘汰、冲突技能合并/降权、失效策略撤回。
  • 产品化表现：Waker 主页"记忆成长时间线"（鱼骨图，每条记忆事件一个节点，含 Skill 生命周期治理节点）；"记忆与学习"入口管理自进化技能；Skill 市场支持上传时选择是否允许自进化、自进化冲突时 AB diff 手动处理；市场 Skill 只读保护 [W2]。
  • 数据：12.3 万项技能中 2.28 万项（约 18.5%）来自系统自进化 [W4]。

【判断】QoderWake 是目前国内把"自进化"做成可视化、可治理、可回滚产品能力最完整的数字员工产品；其差异点不是"能学"，而是"防腐"（capability rot）叙事——承认 7×24 学习会越学越乱，并给出治理机制。这是码道做"持续进化"时应重点对标的设计。

3.9 QoderWake 的战略意图【推断】

  1. 抢占"组织协同入口"而非"个人生产力入口"：常驻钉钉/飞书/企微群，让 Agent 出现在工作真实发生的地方；@Waker 单一机器人 + 后台路由降低了组织采用门槛。
  2. 以"数字员工"叙事对标人力预算："没有人数上限的虚拟人力"，把 Agent 支出从 IT 预算转移到人力/业务预算。
  3. 用记忆与自进化构建时间壁垒："第 90 天专家级经验"、记忆可迁移但沉淀在平台 —— 用得越久越难换。
  4. 通过云端工位把 Agent 变成 IaaS 消耗单元：本地默认是获客手段，7×24 与团队共享是上云理由，计算巢/云电脑/Agentic Computer 是承接产品。
  5. 与 Qoder 共用 Harness 底座，把研发场景验证过的长时运行、状态持久化、失败恢复能力复用到全岗位数字员工（BT 财经的解读："做办公 Agent 最贵的部分原本是在真实代码仓库里被逼出来的能力" [W5]）。

4.3 企业上下文的技术与产品要点 [T2][T3]

  • 问题定义：中大型企业内部数据平均约 150PB，最强模型上下文窗口约 100 万 Token，"一股脑塞进去，要么爆掉，要么浪费执行窗口"——核心是压缩。
  • 按组织范围配置：管理员管理公司层面信息，部门负责人围绕团队建知识空间（如"门店运营知识空间"）。
  • 周期性刷新：新决策、新规则、新进展重新处理，避免 Agent 沿用失效规则。
  • 技术参照：开源的个人上下文基础设施 MyContext——按对话节奏切分、整理人物/项目/事实/关系，冲突信息保留多版本并调整可信度。
  • 成本主张（束骏亮）："别人抽象企业上下文可能 10 天、100 万；我们可能 5000 元、3 天" [T2]。
  • 定位（束骏亮）："企业上下文是新时代的数据基建，像数据库一样，不属于任何一个 Agent 产品，而属于企业客户本身" [T6]。

4.4 多人多 Agent 协同能力

  • 富立卡案例（仓储物流包装）：销售每天 300+ 询盘、跨 6 部门；配置查询 / 报价 / 合同三个数字员工，通过企业上下文共享当前业务信息，前序结果带入后续环节，"客户是谁、适用哪套规则、前一步确认了什么，都不能每到一个 Agent 手里再重新解释一次" [T3]。
  • 协作空间：解决"项目资料和进度分散在不同群聊和文档中，团队成员需反复同步"的问题；协作从人-人扩展到人-Agent、Agent-Agent [T1][T2]。
  • 组织"三重障碍"框架（陈宇森）：不懂（无企业上下文）→ 不敢（安全）→ 不能（优秀个体经验无法复用为组织能力）[T2]。这与 QoderWake"经验到能力"、Qoder"Skill 自进化建议"是同一命题的不同侧面。

4.5 千问办公的战略意图【推断】

  1. 把"企业上下文"做成独立的数据基础设施层，成为所有 Agent（含第三方）的必经之路——"Context is All You Need"，上下文即护城河 [T2][T7]。
  2. 以钉钉的 IM/组织架构为分发渠道，用"数字员工工牌"把 Agent 纳入企业组织与权限体系，解决大企业"安全、可控、可定制"的采购顾虑。
  3. 原子化嵌入而非替代：以机器人、弹窗、按钮形态嵌入既有 IM 和业务系统 [T9]，降低替换阻力，扩大触点。
  4. 硬件收集外部上下文：QwenNote 是"上下文增量收集入口"，未来还有眼镜等 [T2]。
  5. 对阿里云的带动：企业上下文的压缩/结构化处理、Managed Agents 云端沙箱、安全中心审计日志均为云上持续负载；"上下文一旦整理好，更换平台需重新处理的数据、集成和权限配置会增加"（品玩）[T3]。

7. 对华为云码道 CodeArts 的洞察启示与观点（对应 PPT 底部蓝条）

以下为分析建议，供内部讨论取舍。

7.1 研判

  1. 对手已把"多人多 Agent 协同"当作 Coding Agent 的下一个主战场，而非可选功能。Qoder 项目/讨论、QoderWake 群组、千问办公协作空间在同一周发布，是有组织的战略动作。
  2. 对手的短板在"研发管理深度"：Qoder 的项目只是轻量 Issue 看板，无需求/迭代/评审/流水线/制品等 DevOps 闭环；结论回写靠人工；成员靠链接邀请；Agent 不可跨成员共享。这恰是 CodeArts 作为一站式 DevOps 平台的存量优势。
  3. 对手的长板在"Agent 常驻组织 + 记忆进化 + 云端工位"叙事：QoderWake 的五层记忆、Anti-Rot 治理、成长时间线、"第 90 天专家级"是目前最完整的自进化产品化表达。

7.2 观点与建议

# 观点 具体建议
1 以"项目"为一等实体而非"会话" 码道应把 Agent 会话、讨论、任务天然挂在 CodeArts 已有的项目 / 需求 / 迭代 / 代码仓 / 流水线对象上，让 Agent 能读写需求、评审、流水线状态，做到"讨论结论自动回写需求/任务"，而非 Qoder 式人工回写
2 多层记忆是研发场景的天然优势，应先做深 定义 个人记忆（开发者偏好）→ 项目/代码库记忆（架构、约定、测试命令）→ 团队/群记忆（评审共识、口径）→ 企业记忆（编码规范、安全基线、架构资产、合规） 四级，明确每级的写入门槛、可见范围、版本回滚与冲突治理；对标 QoderWake 的"最小必要范围"原则与 Anti-Rot 治理，并补上对手尚未打通的"企业级"一层
3 数字员工 = 有身份、有权限、有成长轨迹的 Agent 借鉴千问办公"工牌"（部门、负责人、授权范围、生命周期、可停用、可审计）和 QoderWake"成长时间线"（记忆/技能演进可视化、自进化产物可回滚），把 Agent 纳入企业 IAM 与审计体系，这是政企客户的采购前提
4 多 Agent 团队要绑定研发 SOP 以"需求分析 Agent → 编码 Agent → 测试 Agent → 评审 Agent → 人工验收"的研发流水线式协作为默认模板，Leader 拆解、成员并行、失败回传、人工门禁；支持团队级 SOP/协作指令的沉淀与复用（对标 Waker 群技能 / WakerFlow）
5 IM 是入口，不是终点 打通 WeLink 等企业 IM，实现"群里 @ 一个机器人、后台路由到多个专业 Agent、结果回群并沉淀记忆"的 @Waker 模式；同时保证结论回流到 CodeArts 项目对象，避免知识只留在群聊
6 云端工位是带动通算的抓手 提供"Agent 常驻工位"（云主机 / 云桌面 / 沙箱）作为码道数字员工的默认运行环境，明确 CPU/内存/存储/网络按用量计费模型（对标 Qoder 沙箱按秒计费、5%–10% 占比），把研发 Agent 的 7×24 值守（告警分诊、CI 失败初诊、依赖升级、代码巡检）变成持续性云负载；配合鲲鹏/昇腾算力与对象存储做"算网存协同"的差异化
7 用"执行即经验"补齐持续进化 把每次 Agent 任务的轨迹（工具调用、验证结果、人工纠正、重做）结构化为可学习信号，归因沉淀为记忆 / Skill / 验证规则 / 流程模板，并提供治理（降权、合并、撤回、回滚）与可视化；先在"代码评审规则"和"测试策略"两类高频、可验证的场景落地
8 与对手错位：深度 vs 广度 阿里三线并进、覆盖全岗位；码道应聚焦"研发全流程 + 企业级治理"的深度，做到"Agent 团队能在 CodeArts 内完成一个需求从提出到上线的闭环"，再向 IM、办公扩展

7.3 一句话观点（可直接放 PPT 蓝条）

阿里正把 Coding Agent 从"个人工具"升级为"常驻云端、拥有记忆与身份的组织成员"，并以项目/讨论、IM 群组、企业上下文三条线抢占多人多 Agent 协同入口；码道 CodeArts 应依托 DevOps 全流程对象与企业级治理，做深"项目为中心的人机团队协作 + 个人/项目/团队/企业四级记忆 + 云端常驻工位"，把研发 Agent 的持续运行转化为华为云通算与智算的增量负载。
