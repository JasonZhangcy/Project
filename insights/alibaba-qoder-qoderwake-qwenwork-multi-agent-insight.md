## 0. 一句话结论（PPT 标题候选）

**阿里正在用"一个 Harness 底座 + 三个协作入口"抢占"人 + 数字员工"的组织级工作现场：Qoder 管研发项目现场，QoderWake 管 IM 群聊里的 7×24 数字员工，千问办公管企业上下文与跨部门协作；三者最终都把 Agent 的长期运行、记忆和上下文沉淀到阿里云上，把 Agent 的"工作时长"变成云的 CPU、存储和网络消耗。**

## 1. 背景：阿里 Agent 产品线的组织与关系

| 维度 | Qoder（新 Qoder 桌面端） | QoderWake | 千问办公（QwenWork） |
|---|---|---|---|
| 归属 | ATH / Qoder 产品线，丁宇（叔同）负责 | 同属 Qoder 家族 | 千问办公事业部（原悟空事业部升级），陈宇森负责，他同时负责钉钉 |
| 定位 | "以编程智能体为核心引擎、面向所有人的智能体平台" | "AI 数字员工运行时平台"，生产可用、安全可控、持续进化 | "业内首个企业级 Agent 产品" |
| 底座 | Qoder Agent Harness / Qoder CLI | 运行在 Qoder CLI 上，与 Qoder、IDE、JetBrains 插件共用 Harness | 以 QoderWork 为主要底座，整合悟空、MuleRun |
| 规模数据 | Qoder 全球用户超过 600 万，服务超过 10 万家企业；IDC 口径下阿里云在中国 AI 编程市场份额 47.6% | v1.0 发布时平台已沉淀 27.6 万条记忆、12.3 万项技能；公测三个多月诞生近 10 万个数字员工、约 2000 万次有效指令（社区文章口径，原文摘录不完整） | 上线约一个月用户超过 3000 万（媒体口径）；企业用户占比超过一半 |

【事实】阿里集团层面要求"未来集团新推出的 Agent 尽量复用 Qoder CLI 的能力"。QoderWork 在内部赛马中胜出后被并入千问办公，而 Qoder 团队又推出"不止于编程"的通用版 Qoder。
【推断】这意味着三款产品**底层同源（同一套 Harness、Sandbox、Memory）**，上层按场景切分：研发、数字员工、企业办公。竞争与互补并存，但都向阿里云汇聚算力。

## 2. 三款产品的功能分析

### 2.1 Qoder：项目（Projects）+ 讨论（Discussion）+ 自定义智能体 / 智能体团队

**发布信息【事实】**
- 2026-09-23 云栖大会发布，同日写入 Qoder CN 更新日志："项目与讨论（企业版）""智能体团队（企业版）""云端自动化""Skill 自进化建议"。
- 目前为内测状态，率先向 Qoder Teams 和 Enterprise 订阅用户开放。
- 丁宇原话："核心是让讨论发生在任务现场，人与模型共享上下文，讨论历史与讨论资产都沉淀在任务上，人不必再做智能体的'搬运工'。"

**项目（Projects）功能要点【事实】**
| 能力 | 说明 |
|---|---|
| 项目创建 | 项目名称、目标描述、可选关联 Repo URL（代码仓库没确定也能先建项目）；支持"使用 Agent 创建项目" |
| Issue 管理 | 标题、目标、背景、完成条件、优先级、状态；支持连续创建 |
| 看板 | 状态流：待规划、待开始、进行中、待验收、已完成、已取消；支持筛选、描述摘要卡片 |
| 成员 | 目前只能通过邀请链接加入，不能从企业通讯录直接添加 |
| 与讨论联动 | 从 Issue 一键"发起讨论"，标题和描述自动带入；讨论结论需**人工**记录回 Issue |

**讨论（Discussion）功能要点【事实】**
| 能力 | 说明 |
|---|---|
| 参与者 | 项目成员 + Agent / Agent Team；可通过分享链接邀请 |
| 上下文 | 附件（设计文档、截图）、引用回复、@人 或 @Agent |
| Agent 参与 | @Agent 让它分析资料、比较方案、补充测试用例；可"打开执行对话"查看 Agent 的执行记录、响应和状态 |
| 决策沉淀 | "关键消息"标记，右侧 Key messages 页签集中查看；搜索消息、置顶讨论 |
| 权限边界 | **只有 Agent 的拥有者可以 @ 它**，不能调用其他成员的 Agent |
| 运行位置 | 允许在 Issue 和讨论中使用的 Agent **在拥有者本机执行，需要设备保持在线** |

**自定义智能体 / 智能体团队【事实】**
- 自定义智能体：保存指令、默认模型、权限、Skills、MCP、Plugins、工具白名单/黑名单，可复用于同类任务。
- 智能体团队：1 名负责人 + 1 到 4 名成员；通过"协作指令"定义分工；负责人拆解、分派、汇总，交人审阅；团队任务同样在当前设备执行。
- 相关能力还有：CLI Agent Teams（main Agent + teammate + shared Task list + SendMessage）、Quest 的 Experts 模式（Team Lead 自动组建前端、后端、QA、评审专家并行执行）。

**配套能力【事实】**
- 云端自动化：有可用云环境的账号可通过对话或配置创建定时任务，在桌面端查看执行记录。
- Skill 自进化建议：会话结束后从可复用经验中生成 Skill 创建或更新建议，确认后执行。
- 企业版：SSO、角色、群组、资源配额、共享资源包池化、Plugin/Skill 统一下发、Plugin Marketplace、知识中心（QMind）、度量与洞察。
- 定价：Teams 40 美元/席位/月（含 3000 Credits）；Enterprise 20 美元/席位/月（不含 Credits，另购组织共享资源包）。

**产品判断【推断】**
1. **形态**：Qoder 把"Linear/Jira 式的轻量项目管理 + Slack 式讨论 + 编码 Agent 执行"放进同一个桌面工作台，本质是把**任务上下文**变成人与 Agent 的共享上下文。
2. **当前短板**：
   - Agent 在个人本机运行，是"个人 Agent 带进群"，不是"团队共享 Agent"，协作深度受限；
   - 讨论结论需要人工回写 Issue，还没做到"讨论→拆单→自动派给 Agent→验收"的闭环；
   - 成员只能靠链接邀请，还没接入企业通讯录，项目管理能力（迭代、依赖、工时、度量）远弱于专业 DevOps 平台。
3. **演进方向**：Agent 迁移到 Cloud Agents 云端运行（让共享 Agent 7×24 在线），讨论结论自动生成 Issue 或 PR，项目与 QoderWake 的"项目记忆"打通。

### 2.2 QoderWake：IM 里的 7×24 数字员工团队

**发展时间线【事实】**
- 2026-04-30 发布邀测（同时发布 Qoder 移动端），首个岗位"数字程序员"已在阿里内部上岗，单条问题根因分析从 30 分钟降到 2 分钟。
- 2026-05 v0.1 全球公测，6 类预置岗位。
- 2026-06 上架阿里云计算巢，一键部署到用户自己的阿里云账号和 VPC。
- 2026-09-03 至 09-08 v1.0 正式发布："v0.1 是招一位数字员工，v1.0 是组建一支数字员工团队"；Mac、Windows 客户端，支持部署到云主机。
- 2026-09-10 @Waker 支持企业微信，至此覆盖钉钉、飞书、企业微信三大 IM。
- 2026-09-16 远端 Waker 交互持续优化，支持创建 Waker、连接聊天渠道、运行任务时选择本地或远程设备。

**数字员工五层模型【事实】**
身份（角色档案，可编辑、可用 git 管理的纯文本人格档案）、记忆（长期上下文）、技能（Skills/连接器）、分工（复杂任务拆解）、权限红线（允许/询问/禁止三档，高危操作弹审批卡片）。
关键设计："员工和工位分离"——员工保存身份、记忆、技能、权限；工位提供运行环境，可以是本地电脑，也可以是云端沙箱。换设备、换模型、换工位，员工不变。

**多人多 Agent 协同【事实】**
| 能力 | 说明 |
|---|---|
| Waker 群组 | 多个本机或**远程** Waker 加入同一群组，指定 Leader 接任务，也可 @ 指定成员；成员可独立配置模型和工作目录 |
| 群技能与协作 SOP | 用群技能和 SOP 明确分工；结构化多步计划（Plan-stage）、动态重规划、执行失败恢复、执行中追问 |
| 产物归集 | 按成员和共享目录归集任务产物；统一任务看板（列表/泳道）查看对话、群聊、WakerFlow、自动任务 |
| WakerFlow | 自然语言生成多步骤工作流，交给不同 Waker 协作；支持定时、事件、API 触发；节点级输入、思考、工具调用、输出可观测；版本与回滚 |
| 自主工作 | 定时、GitHub Webhook 等事件、API 触发器，主动开工 |
| 公开项目 | 同一账号下所有 Waker 共享项目上下文和产物 |

**结合 IM 的能力【事实】**
- @Waker 覆盖钉钉（机器人、个人、AI 助理）、飞书、企业微信、微信、QQ。
- 四项核心 IM 协作能力：历史消息获取、任务、群记忆、话题整理。
- 依托 IM 开放能力（钉钉 DWS、飞书机器人与 CLI、企业微信 CLI），在群内查资料、写文档、处理表格、排日程；企业微信 CLI 开放后两周内完成接入。
- 工程细节：一个机器人可按会话路由到不同 Waker 或团队群组；配对/开放两种接入策略；消息身份感知（识别渠道和发送者）；钉钉"过程叙述"实时推送进度；IM 回复附文件变更摘要；IM 中禁止直接执行系统命令，仅能用 /wake 等专用指令；文件上限提升到 100MB。

**长期记忆与持续进化【事实】**
- 已有五种记忆范围：

| 范围 | 适合保存 | 生效范围 |
|---|---|---|
| 个人记忆 | Waker 的长期职责、输出偏好、通用规则 | 该 Waker 后续相关任务 |
| 项目记忆 | 目录结构、项目约定、测试命令、稳定业务背景 | 选择了该项目的任务 |
| 群共享记忆 | 群内所有成员都应复用的事实、约定、结论 | 当前 @Waker 群聊 |
| 成员记忆 | 某位群成员的职责、偏好、协作习惯 | 当前群聊中的该成员 |
| 单聊记忆 | 机器人与该成员单聊的长期上下文 | 当前 @Waker 单聊 |

- 记忆机制：自动沉淀（回复完成后、空闲轮次后台沉淀用户画像、项目定义、长期目标与约束）、手动编辑、每日自动整理与去重、语义检索、`MEMORY.md` 版本快照与整份回滚、记忆时间线；遵循"最小必要范围"原则（项目规则不写进个人记忆、成员偏好不写进群共享）。
- 记忆存储：**默认本地存储、不上传云端**（CN 版文档）。
- 自进化：
  - Memory 自进化：记忆根据使用情况自动演进；
  - Skill 自进化：复杂任务成功完成后复盘，优先更新已有 Skill，必要时新建；上传的 Skill 可选择"允许自进化"；冲突时用 AB diff 视图人工合并；
  - 成长轨迹：Waker 主页"鱼骨时间线"展示记忆与 Skill 演进节点，含 Skill 生命周期治理节点；Skill 血缘视图展示"项目 → Waker Skill"的贡献关系和引用、使用次数；首页展示入职天数、任务数、工作热力图。

**云端能力【事实】**
- 部署形态：本地（Mac/Windows/Linux）；云电脑（推荐无影云电脑）；Linux ECS（Web UI 端口 19820，SSH 隧道或放通端口）；阿里云计算巢一键部署（运行在用户自己的账号和 VPC，弹性伸缩、按量付费）。
- 远程 Waker：Waker 可以运行在同账号可见的另一台设备上（包括云主机），本地和远程 Waker 可混编进同一个群组；创建 Waker、连接 IM、运行任务时都可以选运行环境。
- 家族云底座：Qoder Cloud Agents（QCA）1.0 于 2026-09-17 发布，定位"一站式云端 Harness 托管平台 / Agent as a Service"：隔离 Sandbox、长任务可恢复、弹性扩缩容、Batch 调度、Memory 与 Dreaming（夜间整理记忆，"把个人经验逐步沉淀为可复用的组织知识"）、观测评测、Outcome 评估、Cloud Use（以受治理身份操作云资源）；Qoder CLI 的 `--remote` 模式把任务放到 Qoder 管理的云端 VM（"独立的 CPU/内存/网络配额"）。

**问题：能否演进为"个人-群-项目-企业"多层记忆？【推断】**
- QoderWake 已具备**个人、项目、群、成员、单聊**五层，唯一缺的是**组织/企业层**。企业层目前分别散落在：Qoder 企业版"知识中心"、QoderWake"知识库"、QCA 的"Memory + Dreaming 沉淀组织知识"、千问办公的"企业上下文"。
- 可以预期的演进路径：
  1. 记忆从"本地文件"走向"云端托管"（与 QCA Memory Store 打通），才能在多设备、多 Waker、多成员之间共享；
  2. 在群记忆之上增加"部门/组织记忆"，与企业身份体系（钉钉通讯录、SSO 群组）绑定权限；
  3. 引入冲突与可信度管理（千问办公开源的 MyContext 已做到：冲突信息保留多版本、调整可信度）；
  4. 自进化 Skill 从"Waker 私有"升级为"组织资产"（Skill 血缘视图已为此铺路），由管理员审核后统一下发。
- 结论：**多层记忆是阿里这三款产品正在收敛的方向，谁先把"企业级、可治理、可共享的记忆层"放到云上，谁就拿到 Agent 时代的组织数据入口。**

### 2.3 千问办公：企业上下文 + 数字员工 + 协作空间

**云栖大会发布（2026-09-22）【事实】**
| 能力 | 说明 |
|---|---|
| 企业上下文（Enterprise Context） | 面向企业的上下文数据管理产品：接入钉钉、飞书、企业微信的文档与消息，以及 Salesforce、SAP 等业务系统历史数据；压缩、结构化、周期性刷新；内置专属模型降低 Token 成本；按组织范围配置（管理员维护公司级信息，部门负责人维护团队"知识空间"） |
| 数字员工 | 名称、所属部门、负责人、岗位职责、授权范围、生命周期；可被识别、授权、停用，执行记录追溯到身份；可部署在钉钉等 IM |
| 协作（协作空间） | 关联群聊、文档、知识库；按需加入团队成员和数字员工；人与人、人与 Agent、**Agent 与 Agent 之间沟通分工**；产出与进度统一沉淀在空间里 |
| Managed Agents | 千问 AI 平台的托管运行时：模型、指令、工具、运行环境、凭证；云端容器沙箱、会话状态和事件历史服务端持久化；企业已有 Agent 也可接入 |
| 应用 | 企业和 SaaS 厂商把业务系统以应用形式接入，保留原界面和数据，Agent 结果可修改并保存回业务系统；宣布接入阿里云上的 Salesforce |
| 安全中心 | 执行前沙箱划定边界、执行中审批和拦截高风险操作、异常后操作记录和恢复；结合钉钉安全体系做最小权限、敏感信息识别、全程审计 |
| 硬件 | QwenNote A2 录音卡（1199 元）、桌面机器人 Eva（899 元），定位"外部上下文入口 + Agent 唤起入口" |

**典型案例【事实】**
- 富立卡：查询、报价、合同三个数字员工通过企业上下文共享信息，围绕同一笔业务接力（多 Agent 协同 + 按岗位最小权限）。
- 古茗：飞书文档、知识库、答疑群、培训日程整理成"门店运营知识空间"，服务近万名一线员工。
- 金龙鱼：菜品提案从多人数天 300 多个步骤缩短到数小时。
- 新签客户：益海嘉里金龙鱼、一汽丰田、中国数联、方达律所、传化集团、横店东磁、国邦医药等。

**高管观点【事实】**
- 陈宇森：Agent 落地企业"要懂业务，要像人一样在组织内协同，每次执行要有边界、可追溯"。
- 束骏亮：上下文会成为 AI 办公的核心竞争点——即使 1M token 窗口也装不下一个项目的聊天、文档、听记和图纸；关键是找出与当前任务直接相关的上下文，形成 AI 友好的数据结构，让 Agent 逐步探索。

## 3. 战略意图洞察：为什么三款产品都在做"多人多 Agent 协同 + 项目"

### 3.1 Qoder：从"个人编码工具"升级为"团队研发工作台"，把席位生意做成组织生意

1. **抢研发协同入口**【推断】：项目 + Issue + 看板 + 讨论，是在 IDE/Agent 工作台里长出一个轻量的研发项目管理层，与 Jira、Linear、云效、CodeArts Board 争夺"需求到代码"的上游入口。一旦讨论和决策沉淀在 Qoder 里，Agent 执行也就留在 Qoder。
2. **从个人订阅到企业订阅**【事实+推断】：项目、讨论、智能体团队都只在 Teams/Enterprise 开放；Enterprise 席位不含 Credits，需要购买组织共享资源包——协同功能是推动**企业版转化和组织级 Credits 池化消费**的抓手。
3. **Agent 资产化**【推断】：自定义智能体、智能体团队、Skill 自进化建议，让团队的研发经验沉淀为可复用的 Agent/Skill 资产，提高迁移成本。
4. **为云端托管铺路**【推断】：现阶段 Agent 在本机执行、要求设备在线，这是明显的过渡形态；下一步大概率切到 Cloud Agents 云端执行（"云端自动化"已经要求"可用云环境"），协同规模越大，云端运行时消耗越大。丁宇在 2025 年云栖就判断："云端异步任务成为主流，云端资源消耗倍增。"

### 3.2 QoderWake：把 Agent 从"会话"变成"常驻员工"，让 Agent 的工作时长变成云资源消耗

1. **占领 IM 协作现场**【推断】：借钉钉、飞书、企业微信的开放能力，把 Agent 放到组织已经在用的 IM 群里，绕开"让用户换工作界面"的阻力；多 IM 中立策略也让 QoderWake 不受限于钉钉生态。
2. **长期记忆 + 自进化 = 越用越难替换**【推断】：记忆时间线、Skill 血缘、入职天数、工作热力图，把数字员工包装成"有成长轨迹的员工"，用户投入的训练成本就是切换成本；"订阅期过了训练成果不会消失"降低了初期顾虑，但长期看记忆和 Skill 仍沉淀在 Qoder 体系里。
3. **云端战略：7×24 常驻 = 持续的通用算力消耗**【推断+事实】

   | 资源 | QoderWake 场景中的消耗来源 | 阿里云对应产品 / 发布 |
   |---|---|---|
   | CPU / 内存 | 常驻进程、Agent Loop 规划、工具调用、代码沙箱、浏览器/Computer Use、构建测试 | ECS、无影云电脑、Agent Sandbox（创建吞吐 10 万/分钟、深休眠唤醒小于 600ms）、Agentic Computer、倚天 CPU 路线图 |
   | 存储 | 工作区代码、产物、记忆文件与版本快照、会话事件历史、知识库 | 云盘、OSS、CPFS（AI 存储成本降低 69%）、Tair KVCM / KV CacheStore（长上下文缓存） |
   | 网络 | IM 长连接与消息回调、MCP/连接器调用、Git 拉取、模型 API 调用、SSE 流 | VPC、公网带宽、磐脉网卡、跨地域互联 |
   | Token | 多 Agent 并行、群组 Leader 汇总、自进化复盘、后台记忆沉淀 | 百炼 / Qwen 模型 API |

   - 【事实】吴泳铭在 2026 云栖明确提出："Agent 产品正在爆发，其任务规划、状态管理、工具调用等环节极其依赖 CPU，同时海量数据的预处理、编排与吞吐也需要 CPU 完成"，需要"单核性能强、内存带宽高、与 GPU 紧耦合的 CPU"；"Agent 需要长时间执行任务……都会成为云上的'居民'，持续调用算力"。平头哥高慧："Agent 高频瞬时调用，需要算网存一体化算力底座。"
   - 【事实】QoderWake 官方推荐部署在无影云电脑或 ECS，并上架计算巢"运行在你自己的阿里云账号与 VPC 内、按业务规模灵活调整算力、用多少付多少"——这是**把数字员工直接绑定到 IaaS 售卖**的通道。
   - 【假设，示意测算】一家 1000 名研发人员的企业，如果人均配 2 个常驻 Waker，每个 Waker 按 2 vCPU / 4 GiB 云电脑或 ECS 规格常驻，即约 **4000 vCPU、8 TiB 内存的 7×24 常驻通用算力**，外加每个 Waker 数十 GB 工作区与记忆存储、持续的 IM 与模型 API 流量。与传统"人均一台云桌面"相比，数字员工是**在人之外新增的算力需求者**，并且不下班。
   - 【推断】"员工与工位分离"设计的战略含义是：员工（身份、记忆、技能）留在 Qoder，工位（算力）可以随时从本地电脑迁到云端；当企业需要 7×24、需要多 Waker 并发、需要合规隔离时，工位自然迁到阿里云。**QoderWake 是通算资源的需求生成器，Qoder Cloud Agents / Agent Sandbox / 无影 / ECS 是承接器。**
4. **家族协同**【推断】：QoderWake 与 Qoder 共用 Harness，Qoder 的项目/讨论、QoderWake 的公开项目/群组、QCA 的 Memory 最终会在"项目"这个对象上打通，形成"研发项目现场（Qoder）+ 群聊值守（QoderWake）+ 云端执行（QCA）"的闭环。

### 3.3 千问办公：把"企业上下文"做成 Agent 时代的企业数据中台，锁定组织入口

1. **上下文即护城河**【推断】：当模型能力趋同，谁掌握"企业最新、结构化、有权限边界的业务上下文"，谁就掌握 Agent 进入业务流程的钥匙；企业上下文 + 应用接入（SAP、Salesforce）让千问办公成为企业数据面向 Agent 的统一出口。
2. **借钉钉的组织身份与安全体系**【事实+推断】：陈宇森同时负责千问办公和钉钉，数字员工的"部门、负责人、授权、生命周期"天然复用钉钉组织架构；这是千问办公相对 Qoder/QoderWake 的最大差异——**组织级身份、权限和审计**。
3. **协作空间 = 跨部门项目空间**【推断】：协作空间本质上是"泛项目空间"，面向业务团队而非研发团队；人、Agent、Agent 之间的协作沉淀在空间中，为企业上下文持续提供增量数据（QwenNote 硬件则补充线下上下文）。
4. **云与模型消耗**【推断】：企业上下文的压缩、结构化、周期刷新本身就是持续的数据处理负载（CPU + 存储 + 专属模型推理）；Managed Agents 托管运行时和沙箱把数字员工的执行搬到千问 AI 平台（阿里云）上。与 QoderWake 相比，千问办公更偏"数据处理 + Token"消耗，QoderWake 更偏"常驻工位 + 沙箱"消耗。

### 3.4 横向对比

| 维度 | Qoder | QoderWake | 千问办公 |
|---|---|---|---|
| 协作载体 | 项目 / Issue / 讨论 | Waker 群组 + IM 群聊 + WakerFlow | 协作空间 + IM（钉钉为主） |
| 主要协作者 | 研发团队 + 个人 Agent + Agent Team | 人 + 多个常驻数字员工 | 业务团队 + 岗位化数字员工 |

| 上下文 / 记忆 | 任务上下文（Issue + 讨论 + 关键消息）+ 知识中心 | 五层记忆（个人、项目、群、成员、单聊），默认本地 | 企业上下文（公司级、部门级知识空间），云端 |
| 进化机制 | Skill 自进化建议 | Memory 与 Skill 自进化、成长时间线、Skill 血缘 | 企业上下文周期刷新；个人侧"意识"跨会话记忆与技能进化 |

| 主要短板 | Agent 不能共享调用、需本机在线、结论需人工回写 | 记忆默认本地、缺企业级记忆层、跨账号协作弱 | 研发深度弱，偏办公与业务流程 |

## 4. 对华为云码道 CodeArts 的洞察启示与观点

### 观点 1：协作的对象正在从"代码仓库"变成"项目现场"，码道应把"项目"做成人和 Agent 的共享上下文
- 阿里的做法是在 Agent 工作台里"长出"轻量项目管理（Qoder）；码道的优势正好相反——CodeArts 已有需求、看板、代码托管、流水线、测试的完整 DevOps 对象模型。
- 建议：把 CodeArts 的 Epic/Feature/Story/Task、MR、流水线、测试用例直接作为 Agent 的项目上下文；在工作项内原生支持"讨论 + @Agent"，并做到**讨论结论自动生成子任务、自动派给 Agent 执行、自动回写状态与验收**——这正是 Qoder 目前需要人工回写的缺口。

### 观点 2：从"个人 Agent"走向"团队共享 Agent"，关键是云端托管运行
- Qoder 的讨论里只能 @ 自己的 Agent，且 Agent 需要本机在线，这是"个人 Agent 进群"的过渡形态。
- 建议：码道提供**项目级共享智能体和智能体团队**（需求分析、架构评审、编码、代码检视、测试、发布值守等角色），运行在华为云托管沙箱中，由项目成员按权限共同调用，7×24 在线；与 CodeArts 流水线、代码检查、测试计划打通，形成"研发数字员工"。

### 观点 3：IM 是数字员工的工作现场，码道应把研发数字员工放进 WeLink 等 IM
- QoderWake 通过 @Waker 覆盖钉钉、飞书、企业微信，并在两周内完成企业微信 CLI 接入，说明"IM 开放能力 + Agent"是快速进入组织的通道。
- 建议：码道研发数字员工以 WeLink 为主阵地并兼容其他主流 IM；支持群内 @ 派活、历史消息理解、群记忆、话题整理、过程进度推送、产物与变更摘要回传；IM 侧严格限制高危命令，高危操作走审批卡片。

### 观点 4：做"四层记忆"，并把企业级记忆作为差异化卖点
- QoderWake 已有个人、项目、群、成员、单聊记忆，但默认本地、缺组织层；千问办公的企业上下文补上了组织层但偏办公。两者尚未打通，这是码道的窗口期。
- 建议的记忆分层与治理：

  | 层级 | 内容 | 归属与权限 |
  |---|---|---|
  | 个人记忆 | 开发者偏好、编码习惯、常用命令 | 个人 |
  | 群/团队记忆 | 团队约定、评审口径、值班规则 | 团队群 / 研发小组 |
  | 项目记忆 | 架构决策（ADR）、代码规范、测试命令、依赖关系、历史缺陷根因 | CodeArts 项目，按项目角色授权 |
  | 企业记忆 | 研发规范、安全合规基线、通用组件、领域知识 | 企业管理员，跨项目下发 |

  配套能力：云端托管、自动沉淀 + 人工确认、版本与回滚、冲突与可信度管理、成长时间线、Skill 血缘与组织级 Skill 审核下发；记忆与 Skill 作为企业资产可导出，回应客户对锁定的顾虑。

### 观点 5：数字员工 = 新的通算资源需求者，码道应成为华为云通算增长的"需求生成器"
- 吴泳铭判断 Agent 的规划、状态管理、工具调用高度依赖 CPU，阿里已围绕 Agent 负载推出 AgentCore、Agent Sandbox、Agentic Computer、新一代 CPFS，并把 QoderWake 绑定到无影、ECS、计算巢。
- 建议：
  1. 为码道数字员工提供"云端工位"：基于华为云沙箱、云桌面、ECS 和鲲鹏算力的常驻运行环境，一键开通，按"数字员工 × 时长 × 规格"计费；
  2. 记忆、工作区、产物、会话事件落在华为云存储（OBS、EVS、SFS 等），长上下文缓存做成可计费能力；
  3. 设计"员工与工位分离"：免费或低价获取数字员工，通过 7×24 常驻、并发扩展、合规隔离引导企业把工位迁到云上，实现从"席位收入"到"席位 + 通算资源收入"的转换；
  4. 以鲲鹏的多核与高内存带宽为卖点，针对 Agent 沙箱高密度部署与快速唤醒做优化，形成"码道 + 鲲鹏 + 昇腾"的软硬协同叙事，对标阿里"倚天 + 真武 + Agent Sandbox"。

### 观点 6：守住研发纵深，与"办公通用 Agent"形成区隔，同时借力企业上下文
- 千问办公和通用版 Qoder 都在向"面向所有人"扩张，研发场景的专业深度（代码理解、流水线、质量门禁、安全合规、国产化适配）反而是码道可以守住的阵地。
- 建议：码道聚焦"研发全流程的多人多 Agent 协同"，同时开放上下文接口，把企业知识库、文档、WeLink 群消息以"企业上下文"方式供研发 Agent 按需调用；在安全上做到数字员工的身份、授权、生命周期、全链路审计（对标千问办公安全中心），满足政企与金融客户要求。

### 一页 PPT 底部"观点"栏可直接使用的精简版
1. **项目即上下文**：借 CodeArts 全链路 DevOps 对象，打造"讨论→拆单→Agent 执行→自动验收回写"的研发闭环，补齐 Qoder 人工回写的缺口。
2. **共享数字员工上云**：从"个人 Agent 进群"升级为"项目级共享研发数字员工"，云端托管、7×24 在线，进驻 WeLink 等 IM。
3. **四层记忆 + 持续进化**：个人、团队、项目、企业四层云端记忆，配套版本回滚、Skill 自进化与组织级审核下发，把研发经验沉淀为企业资产。
4. **数字员工拉动通算**：以"云端工位"承接数字员工常驻运行，按规格和时长计费，带动鲲鹏 CPU、存储、网络消耗，实现从席位收入到"席位 + 资源"收入。
