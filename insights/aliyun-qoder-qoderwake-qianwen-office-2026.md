## 1. 一页结构可直接使用的文字

标题建议：

**阿里云：Qoder、QoderWake、千问办公打造多人多 Agent 协作入口**

三款产品不在抢同一个功能点。Qoder 抢研发任务入口，QoderWake 抢常驻数字员工和云工位，千问办公抢企业上下文和办公协作房间。云栖大会同期发布的 AgentCore、Agent Sandbox、Agentic Computer、Context Engine，是这三款产品往下接的云底座。

### 1.1 Qoder

**项目**

- 2026-09-23 企业版上线，先向 Teams / Enterprise 内测。项目承载目标、可选代码仓库和 Issue。
- Issue 按待规划、待开始、进行中、待验收、已完成、已取消看板跟踪。仓库可以后补，也可以让 Agent 创建项目。
- 邀请目前只支持链接，不能从企业通讯录直接加人。

**讨论**

- 可从 Issue 发起，标题和描述自动带入。同事、自有 Agent、Agent Team 同场评审方案。
- 结论标成「关键消息」，再手动回写 Issue，继续跟踪执行和验收。
- 讨论里的 Agent 在当前设备执行，设备必须在线。只能 @ 自己的 Agent，不能调用别人的 Agent。

**产品战略意图**

把编码智能体从个人对话框，推进成研发团队的任务系统。项目负责把事拆开，讨论负责人和 Agent 一起做决定，智能体团队负责按角色执行。协作界面先落在桌面端；同日发布的云端自动化，以及独立的 Cloud Agents，负责长任务和定时任务，为执行搬上云留出接口。

### 1.2 QoderWake

**多人多 Agent 协同**

- 每个 Waker 有姓名、岗位、入职档案、权限和可追溯任务。职责差得大时，不堆进同一个员工，而是建 Group。
- Group 用一个聊天入口：Leader 接目标、排顺序、分给成员，进展和结果回到同一条任务。
- 公开项目让同一账号下多个 Waker 共享仓库和目录。并行改代码必须隔离分支或工作树，否则会互相覆盖。

**结合 IM 能力**

- @Waker 接入钉钉、飞书，群聊和单聊都能开工。另外三种触发是定时、事件 / Hooks、API。
- 群共享记忆、成员记忆、单聊记忆分开。群约定不会被某个人的习惯污染，私聊口径也不会自动带回群。

**拥有长期记忆的数字人**

- 记忆已经按范围拆开：个人记忆、项目记忆、群共享记忆、成员记忆、单聊记忆。话题只整理一轮讨论，不等于长期记忆。
- 记忆可查看、手改、删除、按版本回滚。鱼骨时间线同时记录记忆和 Skill 的演进。空闲间隙会后台沉淀用户画像、项目定义、长期目标。
- 自进化把成功任务复盘成 Skill，优先更新已有 Skill。防腐机制负责降权、合并、撤回过时记忆和冲突技能。
- 厂商口径（截至 2026 年 9 月初）：沉淀 27.6 万条记忆、12.3 万项技能，其中 2.28 万项来自自进化。
- 还没有单独的「企业记忆」层。组织级知识目前走知识库、公开项目；企业级上下文产品在千问办公和云上的 Agent Context。

**产品战略意图**

把 Agent 做成必须在线的组织成员，而不是随手打开的工具。身份、记忆、技能、权限属于「员工」，本地电脑或云电脑 / ECS 属于「工位」，换工位员工还在。云端常驻把一次性对话，变成持续占用的 CPU、存储和网络。长期记忆和可追溯的成长轨迹，用来提高迁出成本。

云资源判断需要收住一句：公开材料能确认 QoderWake 可部署在客户自己的云电脑和 Linux ECS 上；不能确认它已经接入云栖大会发布的 Agentic Computer。两者在「专属云工位」这个概念上对齐，产品接入关系仍待核实。

### 1.3 千问办公

**产品功能**

- 2026-09-22 云栖发布企业上下文、数字员工、协作、应用、安全中心。企业上下文把文档、会议、群聊压成当前任务真正要用的那部分，内置模型做压缩和结构化，并随业务更新。
- 公开案例：古茗把飞书文档、知识库、答疑群、培训日程收成门店运营知识空间，服务近万名一线员工。富立卡用查询、报价、合同三个数字员工，经企业上下文共享同一笔业务，串起询盘到合同。
- 协作空间把群聊、文档、知识库和人、数字员工放在一起。人可以和 Agent 讨论，Agent 之间也能分工，产出留在空间里。媒体报道称「项目同场协作」仍在灰度，定位接近企业 PMO，细节少。
- 数字员工有名称、部门、负责人、职责、授权范围和生命周期，执行可追溯、可停用。安全侧有沙箱边界、高危人工审批、误删恢复和敏感识别。
- 更早的「多人工作台」（约 2026-09-07）是另一条线：一句话生成最多百人同时协作的业务流程网页，带角色权限、云端数据库、管理后台和发布。它解决的是轻量业务流，不是研发 Issue。

**产品战略意图**

千问办公不跟码道抢代码生成。它抢的是企业私有数据如何变成 Agent 的上下文，以及人、Agent、业务系统在哪个房间里协作。钉钉、飞书、企业微信是现场，企业上下文是数据底座，托管运行时是执行环境。办公入口一旦形成，研发协作也会被拉进同一套企业上下文。

### 1.4 给码道 CodeArts 的观点

阿里已经把「多人 + 多 Agent」拆成三层入口，码道如果只把代码对话做强，会停在 Qoder 重构前的位置。

建议码道守住自己有、阿里正在补的工程系统，同时补上阿里已经产品化、码道容易只做成聊天记录的三件事：

1. **研发协作房间**：项目、Issue、讨论、Agent 团队放在同一条链上。讨论结论要能标记、回写、验收，而不是停在会话里。
2. **分层记忆**：个人、群、项目先做成可编辑、可回滚的记忆；企业工程上下文单独做，覆盖仓库约定、架构决策、流水线和缺陷，不把办公知识库原样搬过来。
3. **云工位**：长任务、多 Agent 并行、定时巡检放到云上沙箱。用沙箱时长、记忆和产物存储、仓库与 IM 流量带动 CPU、存储、网络。记忆是否离开客户环境，留给客户选。

码道的差异点应是工程上下文，不是再做一个办公 Agent。CodeArts 已经有项目、仓库、流水线、测试和部署，这是 Qoder 用 Issue 看板正在逼近、千问办公用企业上下文覆盖不到的资产。

### 2.2 Qoder：项目和讨论不只是更新日志里的两句话

官方定位（2026 年 9 月工作台发布）：Qoder 是以编程智能体为引擎的智能体工作台。人从亲手写代码，转向委派和验收。Harness 负责规划、执行、验证、纠错；Browser Use / Computer Use 让智能体操作真实环境；插件、Skill、连接器接到代码托管、文档、工单和监控。

2026-09-23 企业版新增的四项，要放在这个定位里看：

**项目**

- 用来组织多人研发：新功能、缺陷、技术改造。
- 创建时写目标和预期结果。Repo URL 可空，之后再补。支持「使用 Agent 创建」。
- Issue 写背景、目标、完成条件，有优先级和状态。看板是进度视图，不是另一套项目管理产品。
- 文档示例是「支付链路可靠性改造」：排查重复扣款、评审幂等方案、补充回归用例拆成三个 Issue。

**讨论**

- 可以独立创建，也可以从 Issue 发起。后者会预填标题和描述。
- 参与者是同事，加上创建者自己的 Agent 或 Agent Team。
- 能加附件、引用回复、@ 人或 Agent。
- Agent 被要求比较方案、列风险、补测试思路。文档明确建议写清边界，例如「本次只分析，不修改代码」。
- 「关键消息」是决策记录。右侧可集中查看，并能跳回原消息。
- 来自 Issue 的讨论，结论要**手动**记回 Issue。系统没有自动把聊天变成任务状态。

**智能体团队**

- 自定义智能体保存指令、模型、权限、Skills、MCP、插件。
- 要进 Issue 和讨论，必须打开「允许在 Issue 和讨论中使用」。
- 多个智能体组成团队后，由负责人分派、协调、汇总，人负责审阅。
- 约束很硬：执行在当前设备；拥有者才能 @；关闭开关会中止未完成协作任务。

**云端自动化与 Skill 自进化，是同一天发布的另外两条线**

- 有可用云环境的账号，可以用对话或配置创建定时任务，在桌面端看记录、继续追问。
- 会话结束后，系统可建议创建或更新 Skill。采纳后进入独立会话，人确认方案再执行。可在设置里关掉。

Cloud Agents 是更完整的云运行时，和「讨论里 @ 一下本地 Agent」不是同一个东西：

- Agent、Environment、Session 由 API 创建。Environment 是带网络和依赖的容器，新账号没有默认环境，要先创建。
- 面向长任务、批处理、定时任务、把 Agent 嵌进业务系统。
- 官方对比表把「长程执行、多 Agent、记忆、Skills 与 MCP」以及「弹性扩缩容、长任务可恢复」标成云端能力；安全侧是隔离 Sandbox、凭证注入、权限和审计。
- 每个 Session 在独立容器里，环境销毁后数据清除。

**对「项目 / 讨论」成熟度的判断**

方向已经清楚，产品仍早：

- 加人靠链接，没有企业通讯录选人。
- Agent 不共享，协作网络是「每人带自己的 Agent 进房间」。
- 执行绑在线设备，笔记本合上，讨论里的 Agent 就停。
- 结论回写是手工步骤。
- 内测，且绑在 Teams / Enterprise。

这不影响战略解读。阿里选择先把「人和 Agent 的共同工作对象」从代码文件改成 Issue，再逐步把执行从笔记本挪到云环境。

### 2.3 QoderWake：数字员工、IM、记忆、云工位

2026-04 邀测文把一位数字员工定义成五层：身份、记忆、技能、分工、权限红线。雇主给名字、岗位和红线。换设备、换模型、换工位，员工身份不变。人格档案是可编辑、可纳入 git 的文本。订阅结束后，训练成果不消失。

底层设计是 **员工和工位分离**：

- 员工保存身份、记忆、技能、权限。
- 工位提供运行环境，可以是本地电脑，也可以是云端沙箱。
- 邀测默认住在用户设备上。代码和记忆上不上云，由用户决定。

1.0（2026-09-07）把它从桌面 Agent 推到工作现场：一句话建岗，预置岗位，Waker 常驻钉钉 / 飞书，@ 即响应，定时 / 事件 / API 触发，统一任务看板，并支持部署到云主机。

**多人多 Agent**

- 一个 Waker 承担清楚的职责。冲突职责拆人，或放进 Group。
- Group：成员互补，指定 Leader，每人有自己的模型和工作目录。用户对团队说目标，Leader 分工，结果仍在同一个任务里。
- 文档里的验证标准写得很具体：谁改文件、谁只读评审、中间确认和最终结果是否回到同一任务。
- 公开项目给同账号多个 Waker 共用；私有项目只给一个 Waker。项目配置保存的是目录和访问关系，不复制文件。
- 自动任务触发时没有人改目录，所以要求路径稳定、设备在线、分支不被别的任务覆盖、连接器权限不过期。

**IM**

- 官方更新日志：通过 @Waker 接入钉钉、飞书，统一管理连接、配对、响应哪个 Waker、工作目录和启停。
- 长任务执行中可以排队、插话、中断、恢复。
- 群聊答疑专员一类岗位，基于知识库在群里持续回答，专家可以在群里纠正，知识可撤回。
- IM 是开工入口，不是通知频道。需求出现在群里，Waker 就在群里接。

**记忆：已经是多层，还不是「企业记忆」**

官方记忆文档的五档：

| 范围 | 保存什么 | 在哪里生效 |
| --- | --- | --- |
| 个人记忆 | 长期职责、输出偏好、通用规则 | 该 Waker 之后的相关任务 |
| 项目记忆 | 目录结构、项目约定、测试命令、稳定业务背景 | 选了该项目或目录的任务 |
| 群共享记忆 | 全群都该复用的事实、约定、结论 | 当前已开通的 @Waker 群 |
| 成员记忆 | 某个群成员的职责、偏好、协作习惯 | 当前群里的这个人 |
| 单聊记忆 | 只属于机器人与该成员单聊的上下文 | 当前单聊 |

使用规则同样重要：

- 几周后的新任务还需要这条信息，才进记忆。一轮输入留在任务或话题里。
- 同一规则只放在最小范围。项目规则不要写成个人通用规则，成员偏好不要写成群事实。
- 适合写可验证规则，不适合写密码、Token、客户隐私、未经确认的推测。
- 自动沉淀不代表正确。来源是系统，仍要人工抽查。
- 回滚恢复的是该范围整份 `MEMORY.md`，不是单条。
- 项目结束可以归档项目并保留记忆。
- 记忆不能替代角色文件、权限、知识库和资源配置。

这直接回答「能否演进成个人 / 群 / 项目 / 企业多层记忆」：

- 个人、群、项目已经是产品能力，而且群内部又拆了共享、成员、单聊，隔离做得比「一个群一个记忆」更细。
- 企业记忆没有同名功能。往上走有知识库、公开项目、Skill 市场，以及千问办公的企业上下文、云上的 Agent Context。
- 所以演进路径更像是：Waker 侧继续做「可执行、可回滚的工作记忆」，企业侧另建「可治理的组织上下文」，两者按任务装配，而不是把企业知识全写进某个员工的 MEMORY.md。

**持续进化**

2026-04 的 Harness 文章把 7×24 的核心风险定义成能力腐化：过时记忆污染上下文，技能过时或互相冲突。对应三层：

- 执行即经验：从多次任务里抽出单次日志没写明的规则，例如「支付模块变更必须保持事务结构」。
- 经验到能力：对话、工具调用、记忆召回、验证结果、用户纠正、重做，统一成可学习信号。再按完整轨迹决定沉淀成记忆、技能、策略、验证器还是工作流。
- 防腐治理：监控、验证、降权、合并、撤回。

2026 年 9 月更新日志把这套机制做成界面：

- 「记忆与学习」里有全局记忆、记忆时间线、自进化技能。
- 鱼骨时间线：每条记忆事件一个节点，点开是版本；节点里包含 Skill 生命周期。
- 空闲轮次后台记忆：对话间隙自动沉淀核心记忆。
- 自进化 Skill：复杂任务成功后复盘，优先更新已有 Skill，必要时才新建。上传的 Skill 可以保持只读，或显式允许自进化。
- Skill 血缘视图展示「项目 → Waker Skill」的贡献，并分开统计引用次数和使用次数。

厂商口径：截至 2026 年 9 月，27.6 万条 Memory、12.3 万项 Skill，自进化占 2.28 万项。数字说明自进化已经在跑，不能说明这些技能的质量。

**云端和通算**

事实：

- 官方有《在云电脑和 ECS 上部署 QoderWake》。目的写明是让 Waker 不依赖本地电脑持续运行。
- 云电脑带图形界面，安装方式和本地一致，默认同机访问，不必开放端口。要关睡眠、休眠、自动关机，机器才算真正常驻。
- Linux ECS 无图形界面，Web UI 走两种方式：安全组放通 TCP 19820，或 SSH 隧道只监听本机。同一实例只能用同一个 Qoder 账号。
- Waker 卡片区分 Local / Remote。远端表示跑在同一账号的另一台设备上。文件、连接器凭据和进程留在那台设备，不复制到当前电脑。
- 运行时底座是 Qoder CLI / Qoder Agent Harness，和 Qoder、Qoder IDE、JetBrains 插件共用。Session 持久化，失败可恢复，Sandbox 限制权限。

分析，不要写成阿里已经这么说：

一个常驻数字员工的资源形态，和 IDE 里问一句的资源形态不同。

| 资源 | 被什么行为拉动 | 产品里的对应物 |
| --- | --- | --- |
| CPU | Agent 循环、验证重试、多 Waker 并行、空闲时的记忆整理和 Skill 复盘 | Group、自主工作、空闲记忆、自进化 |
| 存储 | 会话状态、记忆版本、Skill 与血缘、项目工作树、任务和审计日志 | MEMORY.md 版本、鱼骨时间线、公开项目、任务看板 |
| 网络 | IM 回调、模型调用、Git、MCP / 连接器、远端管理 | 钉钉 / 飞书、ECS 访问、连接器、Remote Waker |

拉动方式有两档，不要混成一档：

1. **客户自购云工位**。现在的云电脑 / ECS 文档属于这一档。客户为「员工不下班」购买并保持开机的计算、系统盘、项目盘和入方向网络。这是通算的直接消耗，但是客户云主机，不是记忆 SaaS。
2. **阿里托管的 Agent 云**。云栖的 Agent Sandbox、Agentic Computer、AgentCore 属于这一档：沙箱创建吞吐、深休眠唤醒、长任务断点、专属云电脑、身份和审计。Qoder 的 Cloud Agents 已经是托管运行时。QoderWake 的工位概念和 Agentic Computer 的「长期在线专属云电脑」同构，公开材料没有写已经打通。

因此，QoderWake 支持云端，**可以**成为通算入口，路径是「常驻工位 + 多员工并行 + 记忆与轨迹越积越大」。它**还不是**一条已经计费到 CPFS / KVCache / 融合网络的产品说明。真要带动存储和网络的规模，还要看工位是否从「客户自己装一台 ECS」走到「托管沙箱按秒伸缩」，以及记忆是否进入 Context Engine 那种跨 Agent 复用的数据服务。

### 2.4 千问办公：企业上下文才是主产品

千问办公从 2026 年 8 月上线起就面向企业场景。媒体称约一个月 3000 万用户、企业用户过半、约 120 个版本。这些是增长口径，用来说明它在抢入口，不能用来说明企业级功能已经成熟。

云栖这一轮（负责人：阿里巴巴集团副总裁、千问办公 CEO 陈宇森）发布的是一套组合：

**企业上下文**

- 定位是上下文数据管理产品，不是再做一个问答机器人。
- 官方问题定义：企业数据很多，Agent 做某件事时只需要最相关的那部分。
- 做法：内置专属模型，低 Token 成本压缩和结构化；随业务变化更新。
- 来源：文档、会议、群聊、知识库。接入不限钉钉，也包括飞书、企业微信。
- 古茗：门店问海报规范时，返回当前任务需要的操作，不返回全部运营知识。
- 富立卡：三个岗位数字员工通过企业上下文共享「这一笔业务」，而不是共享全公司数据。销售每人每天 300 多条询盘、协作 6 个部门，是场景压力，不是效果承诺。

**数字员工**

- 组织身份：名称、部门、负责人、岗位职责、授权范围、生命周期。
- 能被授权，也能被停用。执行记录绑在这个身份上。
- 部署在 IM 里，和人在同一现场。
- 运行依赖企业上下文提供业务信息，Managed Agent 提供工具和托管运行。

**协作**

- 协作空间关联分散的群聊、文档、知识库，按需加入人和数字员工。
- 人与人、人与 Agent、Agent 与 Agent 都在空间里发生。产出和进度留在空间，减少跨群转述。
- 「项目同场协作 / 企业 PMO」只有少数报道，且写明灰度。不能把它写成已经对标 Jira 或 CodeArts 项目。

**应用与安全**

- 应用：企业和 SaaS 把原系统接进来，Agent 改完可以存回业务系统。
- 安全中心：执行前划沙箱，高危操作人工审批，另有误删恢复、权限、敏感内容、可信设备。

**多人工作台**

- 比云栖早约两周。自然语言生成协作网页，角色、任务、数据说清楚即可发布，流程变了继续用自然语言改。
- 例子是达人投放、多店开业筹备，最多百人同时在线。
- 它说明千问办公也在做「多人协作容器」，容器形态是业务网页加云数据库，不是研发看板。

和 QoderWake 的分工：

- QoderWake 的记忆是某个数字员工怎么工作、这个项目和这个群有什么约定，偏执行记忆。
- 千问办公的企业上下文是公司业务此刻是什么，偏组织数据。
- 两者都用「数字员工 + IM」。一个从研发运行时长出来，一个从办公和钉钉长出来。云栖之后，客户会同时看到两套数字员工叙事。

### 2.5 云底座：三款产品为什么同一周出现

李飞飞在 2026-09-22 的框架是 Model、Harness、Context。企业级 Agent 要四件事：持续更新的全域上下文、自主运行和持续进化、人与 Agent 的身份和信任、从静态规则到实时行动。

和本次洞察直接相关的产品：

| 云产品 | 公开能力 | 和三款产品的关系 |
| --- | --- | --- |
| AgentCore | 长任务、失败重试、断点恢复、异步执行；沙箱、身份、审计；统一管理模型、MCP、Skill。口径：任务完成率提升 99%，TCO 降 70% | Qoder Harness、QoderWake 7×24、千问办公 Managed Agent 的托管化版本 |
| Agent Sandbox | 创建吞吐 10 万/分钟，深休眠唤醒小于 600ms，兼容 E2B 和 K8s | 多 Agent 并行时的弹性 CPU，避免每人一台长期开机的虚机 |
| Agentic OS | 口径：Token 降 30% 以上，沙箱密度提升 3 倍。组件含记忆 AgentMemory、上下文压缩 Tokenless | 同样的 Agent 数量，更少的算力和 Token |
| Agentic Computer | 长期在线的专属云电脑，Computer Use / GUI，权限可控、可审计 | 和 QoderWake「云工位」、Qoder Computer Use 同构 |
| Context Engine | 「存储—计算处理—上下文工程」。对话、视频、轨迹、Agent 反馈进入多模态存储，再装配成按需上下文 | 千问办公企业上下文的云化形态 |
| Agent Context | 口径：复杂知识任务准确率提升 50 个百分点，Token 效率提升 3 倍以上；记忆、知识、Skill 可跨会话、跨任务、跨 Agent；单工作空间可调度上万智能体 | 补上 QoderWake 还没有的企业记忆层 |
| CPFS、KV 缓存、融合网络 | 训练和推理的存、算、网协同。KV 缓存承接长上下文和多轮 Agent | Agent 规模上去之后的资源账单，不在应用产品文档里 |

应用层负责让客户愿意把 Agent 留在线上；云层负责让留在线上的 Agent 消耗并优化 CPU、存储、网络和 Token。这个结构比「QoderWake 装到 ECS 上所以卖云主机」更完整，也是码道如果要讲通算故事时应该对齐的层级。

## 4. 战略意图

### 4.1 Qoder：先占领研发团队的任务入口

Qoder 过去的优势是个人编码。项目和讨论改变的是购买理由：从「开发者自己的助手」变成「团队把需求和缺陷交给人和 Agent 一起处理的地方」。

意图可以拆成四步，前两步已经发布，后两步还没做完：

1. 用 Issue 把目标拆成可分配、可验收的工作。Agent 不再只对一个仓库聊天。
2. 用讨论把评审留在工作对象旁边。关键消息是决策，不是聊天记录。
3. 用 Agent Team 把角色固定下来。审查、规划、测试各自有指令和权限。
4. 用云环境和 Cloud Agents 把必须在线的执行，从笔记本换成可恢复的云 Session。

对企业版先开，说明这是组织功能，用来支撑席位、集中计费、共享资源包和知识中心，而不只是个人体验。

### 4.2 QoderWake：用「在线员工」把云资源从弹性问答变成持续在岗

如果数字员工下班就消失，客户买的是模型调用。如果数字员工 7×24 在群里、在仓库里、在定时任务里，客户买的是一个不能关机的工位，加上越来越大的记忆和技能存储。

这就是云端战略和通算的连接点：

- **CPU**：常驻循环、多员工并行、失败重试、后台复盘。沙箱密度和深休眠，是阿里云在降低这档成本，以便规模化卖出去。
- **存储**：记忆版本、Skill、会话、项目工作树、审计。Context Engine 把这些定义成新型数据资产，存储不再只是模型训练的磁盘。
- **网络**：IM 长连接、工具回调、远端控制、仓库同步。Agent 越深入业务系统，东西向流量越稳定。

记忆和自进化是留存机制。时间线让「这个员工成长过」可见；防腐让成长不至于变成负债。客户迁走时，带走的不只是提示词，还有分层记忆、Skill 血缘和岗位档案。4 月的文案已经把这一点说透：时间本身成为产品的一部分，订阅结束训练成果仍在。

企业记忆是下一层，不是这一层的缺页。QoderWake 把范围控得很小，避免一个员工记住整个公司。企业层交给上下文产品，按任务装配。这个分工对码道有用：工程记忆和企业知识不要做成一个大仓库。

### 4.3 千问办公：用企业上下文把办公入口变成 Agent 的数据平面

千问办公的多人多 Agent，依赖的不是一个更强的聊天室，而是「这笔业务现在需要哪段上下文」。富立卡三个员工能分工，是因为查询、报价、合同读到的是同一笔业务的不同切片。

战略意图是：

- 私有数据成为续费和迁移壁垒。模型可以换，企业上下文不容易换。
- IM 成为人机同一现场，钉钉是主场，飞书和企业微信用来避免被说成封闭。
- 协作空间把散落的群和文档收成项目容器，和 Qoder 的 Issue 容器平行，一个在办公，一个在研发。
- 安全中心解决企业敢把执行权交出去。没有身份、沙箱和审批，多 Agent 只能停留在建议。

对通算的拉动比 QoderWake 更偏数据和托管运行时：压缩上下文本身要计算，跨会话记忆要存储，百人工作台要云数据库，Managed Agent 要常驻运行环境。它不直接卖代码编译集群，但会把企业的日常协作流量留在阿里云的办公和 Agent 栈里。

### 4.4 组合在一起

```text
千问办公          企业上下文、协作空间、办公数字员工
Qoder             研发项目、讨论、Agent Team
QoderWake         常驻员工、IM、分层记忆、自进化、云工位
Agentic Cloud     沙箱、云电脑、长任务、上下文引擎、存算网
```

上面三层抢入口，底层把入口变成资源消耗。阿里没有用一个产品做完所有事。码道如果用一个代码助手界面去对标这四层，范围会错。

## 5. 对华为云码道 CodeArts 的启示

### 5.1 协作单元改成「事项」，不要停在「会话」

Qoder 的项目和讨论值得学的是对象，不是界面。

码道已有 CodeArts 的项目、仓库、工作项、流水线和测试。阿里是在 Agent 产品里补一个轻量看板。码道应把 Agent 放进已有工作项，而不是另起一个只有聊天的项目。

最小闭环：

- 工作项带目标、完成条件和仓库。
- 从工作项开讨论，参与者是人和有角色的 Agent。
- 决定可标记，并回到工作项的状态和验收。
- Agent 团队有负责人，审查和修改分权限。

Qoder 现在的三个缺口，码道可以做成差异：

- 企业通讯录直接邀请，而不是只发链接。
- 团队共享的 Agent 可以被授权成员 @，同时保留「谁的 Agent、谁负责」的归属。
- 结论回写尽量结构化，减少手工抄回工作项。

讨论中的 Agent 若仍要求开发者电脑在线，企业场景会断。码道应默认提供云上执行，本机执行作为开发者选项。

### 5.2 记忆按层做，企业层做成工程上下文

QoderWake 已经证明多层记忆能产品化，而且必须限制生效范围。码道建议四层，不把五档 IM 记忆原样复制：

| 层 | 码道里放什么 | 不要放什么 |
| --- | --- | --- |
| 个人 | 某个开发者或某个数字员工的偏好、职责 | 项目规范 |
| 群 | WeLink 群里已经确认的协作约定 | 某个人的单聊内容 |
| 项目 | 仓库结构、分支策略、测试命令、架构决策、缺陷口径 | 一次性排期 |
| 企业工程上下文 | 跨项目的技术标准、流水线规范、安全基线、领域术语 | 全公司办公文档的无差别堆叠 |

每一层都要能看、能改、能回滚，并记录是任务沉淀还是人确认。自动学到的内容默认待确认。自进化优先更新已有 Skill，新建要经过人。过时规则要能降权，而不是只追加。

企业工程上下文是码道相对千问办公的主场。千问办公懂门店海报和报价规则，不懂构建、分支和发布。CodeArts 能把流水线结果、代码评审、缺陷和架构决策装配成「这个需求此刻该看的工程上下文」。这比再做一个通用企业知识库更贴码道。

### 5.3 云工位用来带动通算，记忆主权留给客户

可对客户讲清楚的资源关系：

- **CPU**：云上 Agent 工位。长任务、多 Agent 并行、定时质量巡检、失败重试。弹性沙箱覆盖突发并行，专属工位覆盖必须在线的岗位。
- **存储**：项目工作区、记忆版本、Skill、会话轨迹、构建和审计日志。工程上下文单独计量，不和聊天记录混在一个盘里。
- **网络**：仓库、制品库、WeLink、客户业务系统、MCP。Agent 出网走企业已有的网络和权限，而不是员工笔记本直连。

华为云面对政企时，阿里「默认在设备上、上云由你决定」是必须正视的设计。码道可以提供三种工位：开发者本机、客户专属云主机、华为云托管沙箱。记忆和代码放在哪一档，由组织策略决定，不由产品默认上传。

通算故事因此是：Agent 常驻和多 Agent 并行，让计算、存储、网络从「人打开 IDE 的那几小时」变成「事项存在期间的持续占用」。托管沙箱再把无法预测的并行，变成可休眠、可唤醒的弹性消耗。不要把卖点写成「装一个助手就多买 CPU」。

### 5.4 IM 用 WeLink，但记忆边界先定规则

QoderWake 的 IM 能力真正厉害的是记忆隔离，不是把机器人加进群。码道接入 WeLink 时，第一天就要区分群约定、成员习惯和单聊。否则群机器人会把私人纠正变成全员规则。

IM 里的数字员工应绑定 CodeArts 项目和角色，而不是一个全能群助手。群里 @ 它，打开的是某个项目的任务，执行仍回到云工位和工程上下文。

### 5.5 不要跟千问办公比办公全家桶

千问办公值得看的是结构：上下文产品、组织身份、协作空间、业务系统回写、安全中心。码道对应的翻译是：

- 上下文产品 → 工程上下文
- 组织身份 → 项目里的数字员工，有负责人和停用开关
- 协作空间 → 工作项讨论
- 回写 → 代码、工作项、流水线、测试结果
- 安全中心 → 仓库权限、生产变更审批、审计

办公文档、会议和硬件录音不是码道的主战场。需要企业通用知识时，接华为云已有的办公和知识服务，码道只消费和任务相关的那一段。

### 5.6 一句话立场

阿里用三个入口把人和多个 Agent 放进同一件工作里，再用云工位和上下文引擎把这件事变成持续的算力、存储和网络。码道应把 CodeArts 的工程系统变成第四种入口：研发事项从讨论到交付都有人和 Agent 的位置，记忆按个人、群、项目、企业分层，长任务跑在客户可选的云工位上。

## 6. 事实边界

下面这些容易在汇报时被说满，建议保持原样：

- Qoder 讨论中的 Agent **当前在设备上执行**。云端自动化和 Cloud Agents 是相邻能力，不是讨论功能已经云化。
- Qoder 邀请 **还没有企业通讯录**。Agent **不能被别人 @**。
- QoderWake 的云端部署是 **客户的云电脑或 ECS**。员工与工位分离支持云端沙箱，但是否已经使用 Agentic Computer，公开材料没有写。
- 「记忆不上传云端」出现在帮助中心的快速上手，不是 9 月记忆文档的原文。更准确的说法是：邀测默认在用户设备，上云由用户决定；跑在 ECS 上时，数据在那台客户主机上。
- QoderWake **没有**名为企业记忆的一层。企业级上下文是千问办公企业上下文和云上 Agent Context。
- 27.6 万记忆、12.3 万技能、600 万用户、10 万企业、3000 万用户、AgentCore / Agent Context 的效果百分比，都是 **厂商或媒体转述的口径**。
- 千问办公「项目同场协作、企业 PMO」来自云栖期间媒体报道，并写明灰度。协作空间本身有多篇发布稿，可以当成已发布方向。
- MyContext 开源、千问办公由三款内部产品整合，来自媒体，未见本次检索到的阿里官方产品文档复述。
